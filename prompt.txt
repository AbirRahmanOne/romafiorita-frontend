- Recharts for charts
- i18n for the admin UI: EN default, IT optional

/packages/ui-tokens — both themes as Tailwind presets + CSS variables

/packages/ui — shared primitives (Button, Input, Select, Dialog, Toast, Pill/Badge, Skeleton, EmptyState)

/packages/api-client — typed client GENERATED from the backend's OpenAPI schema
- source: `OPENAPI_URL`, e.g. http://localhost:8000/openapi.json, or a committed openapi.json
- tool: openapi-typescript + openapi-fetch
- never hand-write API types

/packages/mocks — MSW (Mock Service Worker) handlers + seed data based on the design's sample data
- lets both apps run fully before the backend exists
- switch with `NEXT_PUBLIC_USE_MOCKS` / `VITE_USE_MOCKS`

/packages/config — shared ESLint, Prettier and tsconfig

Payments (storefront):
- Stripe.js + Payment Element: cards, Apple Pay, Google Pay, PayPal, Klarna
- The frontend never computes the amount it charges. It asks the backend to create the PaymentIntent and only confirms it.
- Payments are authorised (held) at checkout and captured by the backend when the shop accepts the order.

Quality:
- Vitest + Testing Library; Playwright E2E for both apps, running against mocks
- ESLint, Prettier, typecheck in CI (GitHub Actions)
- Lighthouse CI on the storefront

Hosting:
- storefront: Cloudflare Workers via the OpenNext Cloudflare adapter (wrangler config included)
- admin: static build on Cloudflare (Pages/Workers static assets)
- Provide .env.example files for both apps.

10. ADDENDUM — PRODUCT TIERS, PAYMENTS DASHBOARD, CUSTOM ORDER PAYMENT REQUESTS
══════════════════════════════════════

A) PRODUCT TIERS: Standard · Premium · Luxury
Every product has exactly three tiers. Admins set them up; the storefront shows them from the backend. Tier names are fixed:
- EN: Standard / Premium / Luxury
- IT: Standard / Premium / Luxury (labels in i18n so they can change later)

Each tier has:
- price (integer cents, EUR, all-in incl. delivery as configured)
- short description IT/EN (e.g. "12 roses" / "18 roses" / "24 roses + premium wrap")
- its own photo(s), plus stem count/size notes
- active toggle (an admin can switch off a tier, e.g. Luxury unavailable today)
- optional stock/availability and "Same-day" / "Exact time" eligibility
One tier is marked as the default (usually Premium, which is pre-selected on the product page).

Admin — Catalogue:
- Product create/edit form with a "Tiers" section: three fixed rows (Standard, Premium, Luxury), each with price, IT/EN description, image upload, active switch and a default radio.
- Validation: at least one active tier; prices must ascend Standard < Premium < Luxury (warn, don't block).
- Catalogue cards show the price range ("€49 – €89") and which tiers are active; quick toggle per tier.
- Bulk price edit (e.g. +10% on all Luxury tiers before Valentine's) with a preview before saving.

Storefront:
- Product cards: "from €X" (lowest active tier) plus the tier count.
- Product page: a tier selector shown as three visual cards (name, price, short description). Selecting a tier switches the gallery photo and updates the price and the "what's included" text. Inactive tiers appear disabled with an "Unavailable today" label.
- Cart, checkout, confirmation, tracking, emails and the admin order detail all show product + tier (e.g. "Rosa Classica · Luxury").
- The frontend sends variant_id only; the backend recalculates every price in /cart/quote and /checkout.
- SEO: Product JSON-LD with an AggregateOffer (lowPrice/highPrice) or one Offer per tier.

B) PAYMENTS DASHBOARD (Stripe data via the backend)
Admin → Payments:
- KPI cards: gross sales, Stripe fees, refunds, net, for the selected range.
- Payments table: date, order number, source (Website / Phone order / Custom request), customer + country, method (card, Apple Pay, Google Pay, PayPal, Klarna), amount, fee, net, status (held / captured / failed / refunded / disputed).
- Filters, search, CSV export; click a row → order detail; "Open in Stripe" link.
- Held payments panel: authorised but not yet captured, with time left before the hold expires (cards ~7 days, PayPal 10–20 days, Klarna 28 days) and capture/cancel buttons for OWNER/MANAGER.
- Refunds (full/partial with reason), payouts list + current and pending balance, disputes with deadline countdown.
- Monthly report download (CSV/PDF) for the accountant.
- Florist and Rider roles never see this section.

C) CUSTOM ORDER → PAYMENT REQUEST (so customers trust it)
Use case: the client discusses a custom bouquet with a customer on WhatsApp or email, then sends an official, branded payment link from Roma Fiorita instead of asking for a bank transfer or using a random link.

Admin → Orders → "New custom order" (and from the "New phone order" button):
1. Items: pick catalogue products + tier, AND/OR add free-text custom items (title IT/EN, description, reference photo upload, price).
2. Recipient in Italy (postcode validated), delivery date, time type and slot, card message, hide-sender option.
3. Customer (sender): name, email, WhatsApp number with country code, language (IT/EN).
4. Pricing: items + delivery/time fee + optional discount; the server calculates the final total.
5. Expiry: the link expires after N hours (default 48h); optional internal note.
6. Create → backend creates order RF-YYYY-NNNNN with status PAYMENT_REQUESTED and a secure, unguessable token.

Sharing options after creation:
- "Send via WhatsApp": opens wa.me/<number> with a pre-filled, bilingual message, e.g. "Hi Sofia, here is your Roma Fiorita order RF-2026-00123 (€84). Pay securely here: https://romafiorita.com/en/pay/<token> — the link is valid for 48 hours."
- "Send by email": branded email from ordini@romafiorita.com with the order summary and a "Pay securely" button.
- Copy link, QR code.
- Download a branded PDF "Order summary & payment request" (logo, order number, items with photos, delivery details, total, link + QR, expiry, business contact details).
  Label it "Order summary / Payment request", NOT "Invoice" or "Fattura": the business has no VAT number yet, so no fiscal invoice can be issued. Make the document title configurable so it can say "Invoice" later.

Customer pay page: /[locale]/pay/[token] on romafiorita.com, the OWN domain, never a third-party-looking URL.
- Shows the Roma Fiorita header and footer, order number, items with photos, recipient, delivery date/time, card message, the total in EUR with the customer's local currency estimate, and the expiry countdown.
- Payment via the Stripe Payment Element (cards, Apple Pay, Google Pay, PayPal, Klarna). The order is already agreed, so it is captured automatically once paid (configurable).
- Trust elements: secure-padlock note, "Payments processed by Stripe", business contact + WhatsApp button, statement descriptor ("ROMAFIORITA will appear on your statement"), and a short "How to check this is genuine" note.
- States: unpaid / paid (→ confirmation + tracking link) / expired (→ "Ask us for a new link" WhatsApp button) / cancelled.
- No indexing: the page sets noindex and is excluded from the sitemap.

"Verify an order" page: /[locale]/verify
- The customer enters an order number + email and the site confirms whether the payment request is genuine, showing the amount and status.
- Link to it from the pay page, emails and the PDF.

Admin follow-up:
- Payment requests list with status (sent / viewed / paid / expired / cancelled), last viewed time, resend, edit (only before payment, which regenerates the token), cancel, duplicate.
- Real-time notification when a request is paid; the order then enters the normal lifecycle (Accepted → Awaiting photo → …).
